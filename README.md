I read 283 lines from `bookings.jsonl`. Validation against the Pydantic contract quarantined 21 invalid records across seven defect types: 4 invalid student IDs, 4 total amount mismatches, 3 invalid ticket types, 3 invalid ticket quantities, 3 booked after the event date, 2 missing events, and 2 empty tickets lists. Deduplicating the remaining records quarantined 3 re-sent bookings with the reason `duplicate booking_id` (`B0035`, `B0066`, `B0107`), leaving 259 valid bookings. The duplicate check must follow contract validation to guarantee that only well-formed bookings enter the deduplication state. If deduplication ran first and an invalid booking preceded a valid re-send of the same ID, the defective record would consume the identifier and later get quarantined, causing the subsequent valid booking to be discarded as a duplicate. On this specific dataset, swapping the order does not change the counts because all three duplicated bookings were valid, but on arbitrary streams it risks discarding valid data. Schema drift occurs with `promo_code`, which first appears on `2026-10-20T01:05:00Z`; defining it as `Optional[str] = None` in Pydantic allows earlier records lacking the key to default to `None` without failing. Finally, the booking-level `total` is excluded from `fact_ticket_sales` because the fact table's grain is one row per ticket line, not per booking. Including `total` would create a grain trap: computing `SUM(total)` over the fact would duplicate booking totals for multi-ticket orders, yielding 42,000 EGP (1.34× too much) instead of the true total revenue of 31,285 EGP.
